szpL2E v2.1：逼近上線運營全面改善實作成果

本頁彙整《szpL2E v2.1 實作成果規格性能說明書》內容，在 v2.0 九階段（階段 −1 至階段 6）全面改寫實作的基礎上，選擇性推進「逼近上線運營」所需的六大改善領域：資料持久化、版稅實際結算與資產轉移（EIP-2981）、結構化日誌、防作弊規則擴充、API 版本化、混沌測試框架，並新增階段 7 作為六大領域之綜合一鍵展示。run_all_demos.py 現涵蓋九個階段（階段 −1 至階段 7），單次執行總耗時約 34.9 秒，隨附測試套件由 v2.0 的 47 項擴充至 91 項，全數通過。

摘要

本說明書彙整《szpL2E 一鍵啟動階段化實踐計畫 v2.0》與《szpL2E 專案實踐任務拆解與魚骨圖規劃書 v2.0》基礎之上，針對「逼近上線運營」目標所進行的 v2.0→v2.1 全面改善工程成果。v2.0 已完成九階段（階段 −1 至階段 6）之全面改寫實作，證明整套架構可在零外部依賴的沙箱環境內一鍵展示；v2.1 在此基礎上，選擇性地推進六大類「可運行」與「可承受真實維運壓力」之間落差的改善工程，而非僅止於文件敘述層級的規劃。

v2.1 新增階段 7（launch_phase7.py），將上述六大領域整合為單一可重複執行的一鍵展示腳本：真實終止並重啟核心服務行程、驗證「鑄造→首次出售→二次轉售」的版稅生命週期、真實觸發兩項新防作弊規則、以 /v1 前綴驗證 API 版本化、對真實子行程進行三輪混沌測試循環。

run_all_demos.py 總控腳本現已涵蓋九個階段（階段 −1 至階段 7），單次執行全數成功，總耗時約 34.9 秒（v2.0 時期為 17.6 秒，新增階段 7 之真實子行程重啟與混沌測試序列貢獻約 17.6 秒）。隨附測試套件由 v2.0 的 47 項擴充至 91 項（新增 44 項），全數通過，新增測試涵蓋持久化重啟、版稅結算正確性、防作弊新規則、混沌情境下的不變量驗證。

1　v2.0→v2.1 改版總覽與決策脈絡

1.1　改版動機：從「能展示」到「扛得住」

v2.0 說明書第 8.1 節誠實列出四項沙箱環境限制（無法建置 Tauri 客戶端殼、無法串接真實 IPFS/EVM 測試網、無法大規模壓測），這些屬於環境層級的限制，v2.1 不試圖跨越它們（跨越這條線需要真實網路連線與真實工具鏈）。但在環境限制之內、規則與邏輯層級可以誠實推進的部分，v2.0 仍存在幾個明顯落差：

  1. 狀態全在記憶體：任何一次行程重啟（無論是刻意維護或意外崩潰），所有餘額、NFT 持有、冪等性紀錄全部歸零。
  2. 版稅欄位存在但未執行：v2.0 的 royalty_bps 僅被記錄，從未在任何交易路徑上真正觸發扣款分潤，EIP-2981 語意停留在資料模型層級。
  3. 防作弊規則單薄：v2.0 僅有「連續高難度秒答」一項行為規則，對機器人化刷題、多帳號農場等常見濫用模式毫無防禦。
  4. 混沌測試僅存在於規劃書文字：規劃書提及「混沌模式」構想，但沒有對應程式碼，無法重複驗證系統韌性。
  5. 監控儀表板資訊量不足：v2.0 儀表板僅顯示行程存活狀態與效能規格對照，看不到鏈上資產全貌、風控狀況、故障測試結果。
  6. API 沒有版本化機制：所有端點路徑固定，未來若需要做破壞性變更，沒有平滑過渡路徑。

v2.1 針對以上六點逐一動手，而非停留在規劃層級。

1.2　改版原則：向下相容、可重複驗證、誠實標注

v2.1 全程遵守三項工程紀律：

  • 向下相容：所有 v2.0 既有測試（47 項）與既有呼叫介面（chain_client.py、既有服務端點）維持零修改即可通過；持久化機制透過環境變數 SZP_DB_PATH 選擇性開啟，未設定時行為與 v2.0 完全一致。
  • 可重複驗證：新增功能一律配有對應的真實子行程層級整合測試（而非僅函式層級單元測試），例如「真實啟動 chain-sim 子行程 → mint → SIGTERM 真實終止 → 重新啟動 → 驗證餘額」。
  • 誠實標注：每個新模組的 docstring 明確記載「v2.0 → v2.1 改版動機」與「誠實邊界」，延續 v1.1/v2.0 一貫的邊界誠實原則（規劃書 8.3 節）。

2　六大改善領域逐項規格與實作

2.1　領域 A：資料持久化（SQLite，零外部依賴）

問題：v2.0 全部服務行程（chain_sim.py、settlement_service.py、anticheat.py 內建之風控畫像）狀態皆存於記憶體 dict／set／list，行程重啟即歸零。

方案：新增 src/persistence.py，以 Python 標準庫 sqlite3（WAL 模式）提供通用鍵值快照 + 事件日誌雙用途儲存。透過環境變數 SZP_DB_PATH 選擇性開啟：

行為模式條件
純記憶體（v2.0 相容）SZP_DB_PATH 未設定
SQLite 持久化SZP_DB_PATH 已設定

API 設計：store.put(key, value)（鍵值快照寫入）、store.get(key, default=None)（鍵值讀取）、store.append_event(type, payload)（事件日誌追加，用於區塊鏈重放）、store.replay_events(type)（事件日誌重放，行程啟動時還原狀態）。

驗證方式：tests/test_v21_resilience.py 以 subprocess.Popen 真實啟動 chain_sim.py 子行程、送出真實 HTTP mint 請求、以 proc.terminate() 送出真實 SIGTERM、確認行程真正終止後，於同一資料庫檔案重新啟動新的子行程（模擬崩潰後重啟），驗證餘額與 NFT 持有正確還原。另有未設定 SZP_DB_PATH 之對照組測試，確保 v2.0 相容行為未被破壞。

效能開銷量測：本機 mint 交易延遲於純記憶體模式與 SQLite 持久化模式下對照（各 10 次取樣，皆含 120ms 模擬確認延遲）：

模式平均延遲P95 延遲
純記憶體（v2.0 相容）125.49 ms122.48 ms
SQLite 持久化（v2.1 新增）123.11 ms123.28 ms

持久化寫入開銷落於量測雜訊範圍內（差值 < 3ms，遠低於 120ms 模擬確認延遲之量級），證明 SQLite WAL 模式在本沙箱寫入負載下幾乎零額外延遲成本。

2.2　領域 B/C：版稅實際結算（EIP-2981 落地）與資產轉移

問題：v2.0 royalty_bps 欄位存在於 mint 請求中，但從未在任何交易路徑上真正執行扣款分潤，NFT 也無法轉移所有權。

方案：chain_sim.py 新增 /contract/transfer 端點，實作規則：royalty_amount = sale_price × royalty_bps / 10000，seller_proceeds = sale_price − royalty_amount。版稅受益人固定為該枚 NFT 之首次鑄造者（minter_of 映射），無論轉手幾次皆歸屬同一人，符合 EIP-2981「創作者版稅跨越所有次級市場交易」之核心語意。同一端點亦支援同質化代幣（token_id=0）之點對點轉帳（不觸發版稅邏輯）。

生命週期驗證範例（tests/test_royalty_and_transfer.py::test_resale_pays_royalty_to_original_minter_not_seller）：

步驟操作Alice（創作者）餘額Bob 餘額版稅流向
0Alice 鑄造 NFT，royalty_bps=1000（10%）00—
1Bob 以 100 SZP 向 Alice 購買100.0（90 淨額 + 10 版稅）900.0（1000 − 100）10 SZP → Alice
2Carol 以 200 SZP 向 Bob 購買120.0（+20 版稅）1080.0（900 − 100 + 180）20 SZP → Alice（原創作者，非賣家 Bob）

第二次轉售驗證了版稅正確流向原始創作者而非當次賣家，這是 EIP-2981 語意最容易寫錯之處，已納入獨立測試斷言。結算服務代理端點：settlement_service.py 新增 /settle/transfer，讓使用者透過結算服務代理呼叫鏈端轉移，不需直接持有鏈端連線細節。

2.3　領域 D：結構化日誌（JSON Lines）

問題：v2.0 僅以 print(..., flush=True) 輸出人類可讀文字，無法被日誌聚合系統解析、無法程式化篩選查詢。

方案：新增 src/structured_log.py，每個服務行程取得具名 logger，呼叫 log.info(event_name, **fields) 同時輸出：人類可讀摘要至 stderr（保留終端機 demo 可讀性）；結構化 JSON 記錄至 logs/<service>.jsonl（若設定 SZP_LOG_DIR）。state_restored 事件本身即是持久化機制生效的直接證據——可在日誌中直接看到行程啟動時從資料庫還原了幾個區塊。

2.4　領域 E：防作弊規則擴充

問題：v2.0 anticheat.py 僅有「連續高難度秒答」單一行為規則，無法防禦機器人化刷題或多帳號農場等常見濫用模式。

方案：AntiCheatEngine 由單規則擴充為四項獨立規則協同運作：

規則編號規則名稱觸發條件版本
1簽章驗證HMAC-SHA256 簽章不符v2.0
2連續高難度秒答連續 3 題難度≥3 且作答 <2 秒v2.0
3速率限制滑動視窗 10 秒內超過 20 筆事件v2.1 新增
4裝置指紋群聚同一裝置指紋 60 秒內對應超過 5 個不同使用者v2.1 新增

任一規則觸發即進入 held_for_review（暫緩覆核，非永久封鎖），reasons 欄位記錄觸發之規則名稱組合，供人工覆核追溯。風控畫像可選擇性透過 src.persistence 持久化，行程重啟後風控歷史不遺失，避免「重啟洗白風控紀錄」的漏洞。

規則 3、4 觸發量測（階段 7 展示實測）：速率限制於第 21 筆事件（門檻 20，第 21 筆即觸發）觸發 rate_limit_exceeded；裝置指紋群聚於第 6 位不同使用者（門檻 5，第 6 位即觸發）使用同一裝置指紋觸發 device_fingerprint_cluster。兩者觸發時機與設計門檻完全吻合（門檻值 + 1 觸發），證明滑動視窗計數邏輯正確。

2.5　領域 F：API 版本化

問題：v2.0 所有端點路徑固定（如 /contract/mint），未來若需破壞性變更，沒有平滑過渡路徑。

方案：httpkit.py 之 JsonHTTPServer.route() / route_prefix() 裝飾器改為自動雙重註冊：註冊 /contract/mint 時，同時自動註冊 /v1/contract/mint 別名，兩者導向同一 handler，行為保證一致（同一函式物件，非兩份重複邏輯）。未加前綴路徑保留供既有 v2.0 呼叫端不需修改即可運作；新開發呼叫端建議統一使用 /v1 前綴。此設計為 API 演進過渡期慣例：未來若 v3 需要破壞性變更，可新增 /v2 前綴並存，/v1 與未加前綴標示為棄用而非立即移除。

配套產出完整 OpenAPI 3.0 規格文件（docs/openapi.yaml），涵蓋全部四個服務行程共 16 個路徑定義，含請求/回應 schema、v2.1 新增端點標註、API 版本化政策說明。

2.6　領域 G：混沌測試框架

問題：v2.0 規劃書提及「混沌模式」構想，但無對應程式碼落地，launch_phase5.py 的斷線情境是劇本固定安排的一次性斷線，非隨機故障注入。

方案：新增 src/chaos.py，提供三類可組合故障注入原語：ProcessKiller（依機率對子行程送出終止信號，模擬真實維運中的意外崩潰）、LatencyInjector（呼叫前插入隨機延遲，驗證逾時與重試設定是否足夠寬容）、FaultInjector（依機率讓呼叫拋出例外，模擬封包遺失／連線中斷）。搭配 ChaosReport 彙整注入的故障類型統計與不變量檢查（invariant check）結果——例如「總鑄造量－總銷毀量＝流通供給」「同一 tx_id 只被結算一次」——使混沌測試的「系統扛住了嗎」有一個結構化、可視化的答案。

真實情境驗證（tests/test_chaos.py::TestChaosRealProcessRestart）：對真實 chain_sim.py 子行程進行 3 輪「啟動 → mint → 供給守恆檢查 → SIGTERM 終止」循環，同一 SQLite 資料庫路徑貫穿全程，驗證每一輪重啟後供給數字精確守恆（誤差 < 1e-6）。

2.7　領域 H：監控儀表板 v2

問題：v2.0 儀表板僅顯示行程存活狀態與效能規格對照，看不到鏈上資產全貌、風控狀況、混沌測試結果。

方案：src/dashboard.py 新增五項渲染區塊：自動輪詢刷新（內嵌 <meta http-equiv="refresh">，頁面定時重新載入）；鏈上資產總覽（流通供給、累計鑄造/銷毀、NFT 總數、累計版稅支付總額卡片式呈現）；風控事件區塊（列出目前 held_for_review 狀態使用者與觸發原因）；混沌測試報告區塊（故障類型統計 × 不變量檢查結果並列表格）；持久化狀態標示（行程健康檢查旁標示「持久化」或「純記憶體（重啟即遺失）」徽章）。儀表板產生器維持 v2.0 之靜態 HTML 快照設計哲學，新增區塊皆為可選參數，未提供時自動省略，向下相容 v2.0 呼叫端。

11　已知限制與後續展望

11.1　本次沙箱環境限制（延續 v2.0，v2.1 未改變此類限制）

  • 無法建置真實 Tauri 客戶端殼（無 Rust/cargo 工具鏈）
  • 無法串接真實 IPFS 節點或 Storacha 雲端服務（無網路連線）
  • 無法部署至真實 EVM 測試網（無網路連線）
  • 無法進行大規模併發壓力測試（單機沙箱資源限制）
  • SQLite 持久化為單檔案嵌入式資料庫，不具備分散式高可用能力

11.2　v2.1 完成後，階段 7（依規劃書 T8-01/T8-02）剩餘展望範疇

v2.1 已將以下項目從「規劃構想」推進至「規則層級真實運作」，但完整生產就緒仍待：

  • 真實 Tauri 五端（Windows/macOS/Linux/iOS/Android）編譯與安裝檔實測
  • 真實 Storacha 雲端持久化整合測試（v2.1 之 SQLite 持久化僅解決單機重啟問題，非雲端多節點高可用）
  • 真實測試網（如 Sepolia）合約部署與 Gas 成本實測（v2.1 版稅結算邏輯已可作為合約邏輯參考基準）
  • 大規模併發壓力測試與去中心化計算層（Oracle）整合
  • CoW Protocol／Wormhole Bridge 真實網路交易時序實測
  • 正式 API Gateway 建置（TLS、OAuth2/JWT、標頭版本協商，v2.1 之 /v1 路徑前綴為過渡機制）
  • 真實日誌聚合系統串接（v2.1 之 JSON Lines 檔案為過渡格式，ELK/Loki/CloudWatch 等）
  • 防作弊規則門檻值之真實流量壓測校準（v2.1 門檻為工程經驗預設值）
  • 混沌工程擴大至跨真實網路節點、跨地理區域、磁碟/OS 層級故障（v2.1 僅涵蓋本機行程層級）

11.3　建議下一輪（v2.2 或階段 7 正式）優先順序

依「風險 × 影響範圍」排序，建議下一輪優先處理：

  1. 正式 API Gateway 與身分驗證（TLS + OAuth2/JWT）：目前系統完全信任呼叫端身分主張，是距離「可對外開放」最近的一項風險。
  2. CoW Protocol／Wormhole Bridge 真實測試網探索性測試：規劃書已標注此為風險等級最高的技術項目（Wormhole 曾有重大安全事件），應及早以測試網小額資金驗證路由決策邏輯。
  3. 防作弊門檻值真實校準：v2.1 門檻為預設值，正式上線前需依真實使用者行為分布重新校準，避免誤判活躍使用者或漏放濫用行為。
