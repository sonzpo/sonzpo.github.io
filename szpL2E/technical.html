1　整體架構原則

「無後台伺服器」的正確定義

在正式展開技術選型前，必須先釐清一個關鍵前提：在 szpL2E 目標規模（跨鏈交易、IP 授權市場、課程平台、未來 ERP／預測市場）下，「完全 100% 無任何伺服器」並不現實，也不是業界去中心化應用（dApp）的真實運作方式。合理且可落地的架構目標，是達成「無單一信任伺服器（No Trusted Central Server）」，而非字面上的「無任何運算節點」。

具體而言，szpL2E 應追求以下三項原則：

  1. 無中心化業務邏輯伺服器：撮合、鑑權、資金保管等核心業務邏輯，皆不經由 szpL2E 自營且可單方控制的伺服器處理。
  2. 保留輕量、無狀態、可被任何人重跑的基礎設施：例如 RPC 節點、IPFS Gateway、鏈上事件索引器。這些屬於「去信任化」而非「消失」——任何人都可以自行架設對等節點取代 szpL2E 提供的節點。
  3. 以智能合約與鏈下協定（Intent-Based Protocol）取代傳統後台 API：交易撮合、資產轉移、內容授權等操作，改由使用者用錢包簽署「意圖」，交由去中心化的求解者／中繼者網路執行，最終在鏈上結算。

這也是 CoW Protocol、Wormhole 等成熟去中心化協定自身採用的模式：鏈上結算、鏈下 Solver/Relayer 網路執行、客戶端直接簽署意圖。szpL2E 的架構設計仿照此一模式作為主軸。

2.2.1　防作弊驗證機制與題型權重

驗證機制是本產品最關鍵的護城河。若驗證過鬆，代幣獎勵將淪為無意義的刷題行為，破壞經濟模型與教育信譽。核心設計包含間隔重複測驗（同一知識點在 1／3／7／14 天後重複出現，僅多次間隔後仍正確才給予完整獎勵）、打字與操作速度異常偵測、裝置與行為指紋比對。

題型驗證強度代幣權重
選擇題低（易猜測／易作弊）基礎權重 1x
情境應用題中（需理解與推理）權重 2–3x
實作題／專案提交高（需實際操作與產出）權重 4–6x
企業命題任務最高（企業覆核 + 實作）權重 6–10x ＋企業贊助獎金

2.3　代幣經濟的通縮設計

代幣發放遵循遞減曲線：初期獎勵倍率最高以驅動早期採用，隨使用者等級與代幣總流通量提升，單題可得代幣逐步下修，並與「當期代幣總流通量」動態掛鉤。搭配進階內容解鎖、證書鑄造、抽獎參與等多個消費情境的固定比例代幣銷毀（Burn）機制，形成自我調節的通縮壓力。

指標定義對獎勵的影響
進步係數測驗正確率、實作品質分數的時間序列成長幅度持續進步者獲得倍率加成；停滯或倒退則倍率下修
留存係數跨週期的規律學習頻率（而非單日暴刷）規律學習者獲得穩定倍率；短期爆量後消失者無法累積加成
品質係數實作題／專案的人工或 AI 覆核評分低品質產出無法透過「量」彌補代幣收益

企業贊助任務資金由企業預先儲值於智能合約，平台不代墊、不經手資金流轉，全程鏈上化，進一步降低平台自身的資金壓力與監理暴險。

3　跨平台客戶端架構：Tauri v2

選型理由：szpL2E 需要同時支援 iPhone、Android、Windows、macOS 與 Wasm 網頁五種執行環境，且核心邏輯涉及金鑰管理、加密簽章等高敏感度運算，因此客戶端框架選型以「單一核心邏輯、多端部署、原生等級安全性」為最優先考量。Tauri v2（穩定版 v2.10.1，2026 年 3 月發佈）已完整支援 Linux、macOS、Windows、Android 與 iOS 五大平台，核心邏輯以 Rust 撰寫，是目前唯一能以單一 Rust 核心涵蓋桌面與行動裝置的成熟跨平台框架。

需求Tauri v2 對應能力
五端統一部署iOS 和 Android 目標與桌面共享同一個 Rust 核心業務邏輯，避免邏輯重複開發與分裂維護
Wasm 網頁版前端本為 Web 技術（React／Svelte／Vue），Rust 核心可額外編譯為純 Wasm＋Web 版本
錢包與加密邏輯CPU 密集運算（簽名、加密）交由 Rust 處理，效能較 Node.js 快 10～100 倍
輕量、快速安裝使用系統原生 WebView 而非打包 Chromium，安裝檔可小至數 MB 等級
權限治理v2 引入基於能力（Capability-Based）的權限模型，取代 v1 的一次性 allowlist

3.2　客戶端四層架構

  1. 前端 UI 層：React／Svelte + TypeScript，撰寫一次、多端共用。
  2. Tauri IPC Bridge：前端與 Rust 核心之間透過 invoke／emit 進行進程間通訊。
  3. Rust 核心：涵蓋 szpEX 錢包簽章與金鑰管理（含硬體錢包 HID/USB 通訊）、嵌入式 IPFS/libp2p 節點、本地加密資料庫（SQLite + SQLCipher）、CoW SDK／Wormhole SDK 呼叫橋接。
  4. 編譯輸出：原生路徑編譯為 iOS／Android／Windows／macOS／Linux 五種原生執行檔；另一條路徑將 Rust 核心以 wasm-pack 編譯為 WebAssembly，搭配 WebCrypto API 保護私鑰，形成 Wasm 網頁版。

此設計確保「Web 版」與「原生版」共用同一套 Rust 安全邏輯，而非另外以 JavaScript 重寫一份，避免安全邏輯分裂、難以稽核的風險。次選方案 React Native 會犧牲 Rust 核心跨端共用優勢，不建議作為主架構。

4　去中心化儲存層：IPFS 與 Storacha

單純部署 IPFS 節點無法保證資料長期可得性——若無人執行 Pin 操作，內容可能隨時從網路中消失。2026 年業界實務做法是將「IPFS 內容定址」與「底層持久化網路」結合使用。Storacha（前身為 web3.storage）結合 IPFS 內容定址、Filecoin 長期持久化與 UCAN（User Controlled Authorization Networks）式權限控制。

層級用途技術方案
熱資料電子書封面、課程縮圖、UI 資產IPFS + Storacha（UCAN 授權）
冷資料已購買的完整電子書、課程影片母帶Filecoin 儲存合約（透過 Storacha 或直接 FVM）
個人加密資料使用者筆記、學習進度、私鑰加密備份IPFS 私有加密內容，開放使用者自選 Pin 服務
App 內嵌 P2P 節點點對點直接下載加速、離線優先體驗js-libp2p／rust-libp2p（嵌入 Tauri Rust 核心）

4.3　內容 IP 保護的關鍵設計

電子書與課程內容不應以「明文」形式直接放上公開 IPFS 網路。正確流程為：內容於上傳前先行加密並上傳至 IPFS 取得 CID；解密金鑰透過智能合約進行「購買後授權釋放」，可採 Lit Protocol 式的存取控制條件，或自建門檻式金鑰分發服務；CID 僅作為「加密封包」的定址指標，真正的存取控制邏輯完全落在鏈上，而非由 szpL2E 的伺服器把關。建議至少接入兩個獨立的 Pinning／持久化服務，以分散單一服務中斷或政策變動的風險。

5　szpEX 松鼠坡交易錢包：跨鏈交易核心

5.1　CoW Protocol：同鏈最優價格撮合與 MEV 保護

CoW Protocol SDK 支援意圖式交易（Intent-Based Trading），涵蓋 Swap、限價單、TWAP 與可程式化訂單，並覆蓋 11 個以上區塊鏈網路。採批次拍賣（Batch Auction）機制執行交易，避免使用者交易被搶跑或三明治攻擊；CowShedSdk 讓一般 EOA 錢包也具備智能合約帳戶能力，可實現「一鍵完成：購買課程 + 換幣」等複合交易流程；本身即提供 BridgingSdk，整合多種橋接供應商。

5.2　Wormhole：跨鏈資產橋接

Wormhole TypeScript SDK 支援原生代幣轉移（NTT）、封裝代幣轉移（WTT）、CCTP（USDC 專用）與 Settlement 結算。WTT 協定簡化跨鏈資產轉移流程，適合遊戲資產跨鏈情境；SDK 支援涵蓋 EVM 與非 EVM 鏈（如 Solana、Sui），為未來擴展預留彈性。

5.3　szpEX 整合架構

  1. 使用者於 szpEX 錢包（App 內嵌、非托管）中發起操作，支援軟體金鑰（BIP-39/44，Rust 端加密儲存）與硬體錢包連接（Ledger／Trezor）。
  2. 交易路由決策層依交易類型分流：同鏈換幣走 CoW Protocol SDK；跨鏈資產轉移走 Wormhole SDK；跨鏈＋換幣的複合交易優先走 CoW 的 BridgingSdk，Wormhole 作為底層橋接的備援路由，兩者並存增加路由多樣性與容錯能力。
  3. 最終於鏈上完成結算，szpL2E 全程無需以自營伺服器介入資金流轉。

5.5　社交復原機制（Social Recovery）

私鑰完全由使用者裝置本地加密保管，szpL2E 平台不託管私鑰。為降低助記詞遺失風險，szpEX 建議整合社交復原機制，讓使用者可指定多位信任聯絡人，於私鑰遺失時透過門檻簽章（如 3 取 2）共同批准帳戶復原，不需任何一方單獨掌握完整私鑰。此機制以智能合約帳戶（Account Abstraction）實作，復原流程全程鏈上執行。

6　szpDRX 數位授權交易模組 與 szpERX 數位學習交易模組

szpDRX（數位智慧財產 IP 授權交易）與 szpERX（數位學習課程交易）在技術本質上是「同一套資產化框架」的兩種應用場景，核心設計原則為：內容加密 + 鏈上所有權證明 + 條件式解密 + 版稅自動分潤。

功能技術方案
IP／課程資產鑄造ERC-1155（可複製銷售商品）或 ERC-721（限量版／創作者原版）
版稅自動分潤EIP-2981 搭配智能合約強制執行，二級市場轉售亦可自動分潤原創作者
內容存取控制加密內容存放 IPFS／Storacha，購買後由智能合約觸發金鑰釋放
線上考試防作弊題庫加密，作答結果雜湊記錄於鏈上時間戳；可選用 zk-SNARK 隱私證明
課程遊戲化學習進度以鏈上事件／積分記錄，完課里程碑鑄造成就 NFT

未來擴充方向音樂、圖像、影音等其他數位智財類型更多課程形式（直播課、認證課程、企業內訓）

7　中長期模組技術路線圖：ERP、預測市場與遊戲

ERP 模組

智能合約記帳＋zk-Rollup

延續「智能合約記帳 + 前端 UI」的一致架構路線，採零知識證明技術強化隱私保護，使企業帳務明細不必公開於鏈上仍保有可驗證性。

預測市場模組

條件代幣框架

參考 Polymarket／Gnosis 的條件代幣框架（Conditional Tokens Framework），天然適合與 CoW Protocol 批次拍賣機制結合結算，直接沿用 szpEX 既有交易路由基礎設施。

遊戲模組

跨鏈友善代幣標準

遊戲內資產自設計初期即採用跨鏈友善代幣標準，直接對接 szpEX 已整合的 Wormhole NTT 協定，避免日後資產難以跨鏈流通。

8　風險與現實提醒

⚠ 監管風險

跨鏈橋接、IP 版權交易、教育服務，加上未來規劃的 ERP 與預測市場模組，橫跨證券法、著作權法與金融監理等多重法律領域，建議及早諮詢熟悉加密貨幣與證券法規的專業律師進行合規性審視。本規劃書僅為技術架構研究，不構成法律意見。

⚠ 跨鏈橋接安全風險

跨鏈橋歷史上是駭客攻擊的重災區，Wormhole 本身也曾於 2022 年發生約 3.2 億美元的重大安全事件。szpL2E 於整合跨鏈橋接功能時，務必落實多重簽章機制、第三方安全審計，並評估導入保險機制以降低使用者資產風險。

⚠「完全無伺服器」的體驗代價

採用無後台架構意味著沒有傳統客服系統，也沒有集中式的異常監控機制。szpL2E 需要在 App 內建更完善的鏈上交易狀態追蹤與錯誤恢復流程，來彌補去中心化架構下使用者支援體驗的落差；此部分的 UX 設計難度將顯著高於一般中心化 App。
