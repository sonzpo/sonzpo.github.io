1　Shared Foundation Task Layer (Sprint −1)

From the nine work domains, identify the interface-level tasks that "multiple domains jointly depend on, and where a later change would trigger cascading rework," and freeze their specs first as the common basis for everything downstream. This round adds the Tauri client and performance-spec scope, expanding the shared foundation nodes from seven to eight (F1–F8).

⚠ Why F8 is foundational

The Technical Architecture Plan explicitly defines the client's four-layer architecture and stresses that "the web version and native version share the same Rust security logic." The interface contract for high-sensitivity operations — key management, signing logic — must be frozen before detailed work on Domain 5 (szpEX wallet) and Domain 2 (learning verification) begins, or the risk of fragmented behavior across five platforms will directly undermine the core "no centralized business-logic server" principle. F8, alongside F4 and F6, is one of the three highest-risk foundational nodes this round.

Web3 wallet engineering + protocol integration. Self-custody wallet, CoW/Wormhole dual routing, hardware wallets, social recovery.

Business development + asset-tization smart-contract engineering. ERC-1155/721+EIP-2981, corporate-task integration.

Domain⑧

Domain⑨

Performance-spec sign-off, ops monitoring & operations manual

SRE／technical writing + security audit／educational-integrity QA. Runs across S3–S5, the most concentrated domain at the end of the timeline.

This round adds Domain① (Tauri client) and Domain⑨ (performance sign-off and ops) to the nine domains; Domain① and Domain④ together form the critical path's dual starting point — the client's Rust core is the foundation for wallet and crypto logic, and the decentralized infrastructure is the foundation for smart contracts and storage. Both must have their specs frozen early and in parallel (F8 and F4) before the rest of the domains can proceed in parallel.

4　Two-Tier Verification: Claude AI Verification → Engineering Implementation

Tasks first complete a first-tier verification in a Claude AI environment — confirming the rule logic is internally consistent, the numeric balance is reasonable, or an interactive prototype works — before moving into second-tier engineering implementation.

Mode①

Rule-logic simulation

Verification engine, anti-cheat, state-transition logic; produces a verification memo + a revised rule set.

Mode②

Numeric simulation

Token-economy curves, burn ratios, rate-limit thresholds; produces simulation scripts + data charts + balancing recommendations.

Mode③

Interactive prototype demo

User flows, leaderboard UI, corporate-task posting interface; produces an interactive prototype + a recorded interaction trace.

Mode④

Not applicable (flagged, skipped)

Third-party security audits, real multi-machine network load tests, real-fund cross-chain-bridge tests; produces a spec-review memo.

Mode⑤

Educational-effectiveness simulation

Simulates different learner answering patterns (including deliberate gaming); produces an educational-effectiveness report + a counterexample list.

New scenario

Performance-benchmark comparison

Estimates, based on the chosen technology, whether a theoretical ceiling might exceed the spec target; flags high-risk items and pre-warns when close to the threshold.

16.2　High-Risk Node List

⚠ T0-05　No-Persist private-key security boundary

The Wasm web version and the native version must share the exact same Rust security logic; a poorly designed sandbox boundary could let a plaintext private key leak via serialization, and the web version inherently has a larger attack surface than native. Mitigation: run rule-logic simulation with Claude in Sprint 0 to check the WebCrypto API／wasm-pack boundary line by line, with a security representative required to review.

⚠ T3-02　Layer-2 chain selection

A foundational decision for the entire decentralized infrastructure — once chosen, every smart contract downstream is built on that chain, and rework cost is extremely high if performance or ecosystem fit later proves inadequate. Mitigation: complete technical due diligence on at least two candidate L2 chains during Sprint −1.

⚠ T4-06　CoW BridgingSdk and Wormhole dual routing coexisting

A flaw in the routing-decision layer could cause duplicate charges or routing conflicts for user assets; Wormhole itself suffered a roughly $320M security incident in 2022, making this one of the highest-risk technical items in the plan. Mitigation: exploratory testing with small testnet amounts in S2, and a third-party security audit covering the dual-routing decision logic before launch.

⚠ T1-08　Anti-cheat module integration testing

The core reputational risk for an education product: too high a false-positive rate hurts real learners, too low a detection rate lets the token economy be drained by grinding abuse. Mitigation: simulation scenarios should cover diverse, realistic user behavior patterns, with a human appeal/review channel preserved.

⚠ T2-10　Token-economy engine agent-based stress testing

If the dynamic-adjustment algorithm destabilizes under extreme scenarios, the cost to correct it is higher than under a fixed-amount model. Mitigation: run extreme-scenario simulations first in S0, then scale up real stress tests incrementally, keeping an emergency pause mechanism.

⚠ T8-04／T8-06　Operations manual & troubleshooting reference

With no centralized customer-support backend, the in-app help and FAQ are the only user-support channel; any error (especially in irreversible situations like a lost seed phrase) directly threatens asset safety and platform trust. Mitigation: joint review by legal counsel and the technical writer, with a line-by-line comparison against the source text at final sign-off.

⚠ T7-06　Third-party security audit

Covers smart-contract and wallet/cross-chain integration; audit firms typically need 2–3 months' lead time to book. Mitigation: book an audit firm's slot as soon as the project kicks off, and evaluate insurance mechanisms.

19　Evidence-Tier Continuity: From "Spec Frozen" to "Production Verified"

The risk-mitigation value of rule-logic simulation

Because szpL2E has no existing test suite to use as a regression baseline, this plan's risk mitigation leans primarily on the depth of rule-logic simulation, numeric simulation, and performance-benchmark comparison during Sprint −1/0. szpL2E relies on rule simulation and spec comparison as an "advance safety net," echoing the core principle that "any architectural claim should be tested against reality before it is presented externally."
