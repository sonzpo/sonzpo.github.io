szpL2E v2.1: results of the approaching-production-readiness rewrite

This page compiles the contents of the "szpL2E v2.1 Implementation Results Specification & Performance Report." Building on v2.0's full nine-stage rewrite (Stage −1 through Stage 6), v2.1 selectively advances six improvement domains needed to approach real operating conditions: data persistence, real royalty settlement and asset transfer (EIP-2981), structured logging, expanded anti-cheat rules, API versioning, and a chaos-testing framework — plus a new Stage 7 that serves as a combined one-click demo of all six domains. run_all_demos.py now covers nine stages (Stage −1 through Stage 7), taking roughly 34.9 seconds total in a single run; the accompanying test suite grew from v2.0's 47 tests to 91, all passing.

1　v2.0→v2.1 Rewrite Overview & Decision Context

1.1　Rewrite motivation: from "can demo" to "can take a beating"

§8.1 of the v2.0 report honestly listed four sandbox environment limits (no Tauri client-shell build, no real IPFS/EVM testnet connectivity, no large-scale stress testing). These are environment-level limits, and v2.1 does not attempt to cross them — crossing that line would require real network access and real toolchains. But within the environment's limits, at the rule and logic level, v2.0 still had several clear gaps it could honestly close:

  1. State lived entirely in memory: any process restart — whether a deliberate maintenance action or an accidental crash — zeroed out every balance, every NFT holding, and every idempotency record.
  2. Royalty field existed but was never enforced: v2.0's royalty_bps was only recorded, never actually deducted or distributed on any transaction path — EIP-2981 semantics stayed at the data-model level.
  3. Anti-cheat rules were thin: v2.0 had only one behavioral rule ("consecutive high-difficulty instant answers"), offering no defense against bot-driven farming or multi-account abuse patterns.
  4. Chaos testing existed only as planning-document text: the plan mentioned a "chaos mode" concept, but no corresponding code existed, so system resilience could not be repeatedly verified.
  5. Dashboard lacked information depth: the v2.0 dashboard only showed process liveness and performance-spec comparisons — no on-chain asset overview, risk-control status, or fault-testing results.
  6. No API versioning mechanism: every endpoint path was fixed, leaving no smooth migration path for a future breaking change.

v2.1 tackles each of these six points directly, rather than staying at the planning level.

1.2　Rewrite principles: backward compatibility, repeatable verification, honest disclosure

v2.1 held to three engineering disciplines throughout:

  • Backward compatibility: every existing v2.0 test (47 total) and existing call interface (chain_client.py, existing service endpoints) passes with zero modification; persistence is opt-in via the SZP_DB_PATH environment variable, and behavior is identical to v2.0 when it is unset.
  • Repeatable verification: every new feature ships with a corresponding real-subprocess-level integration test (not just function-level unit tests) — for example, "really launch the chain-sim subprocess → mint → send a real SIGTERM → restart → verify balance."
  • Honest disclosure: every new module's docstring explicitly records its "v2.0 → v2.1 rewrite motivation" and "honesty boundary," continuing the boundary-honesty principle established in v1.1/v2.0 (plan §8.3).

2　Six Improvement Domains: Spec & Implementation

2.1　Domain A: Data Persistence (SQLite, zero external dependencies)

Problem: every v2.0 service process (chain_sim.py, settlement_service.py, and the risk-control profile built into anticheat.py) kept state in in-memory dicts, sets, and lists — restarting the process reset everything to zero.

Solution: a new src/persistence.py module provides dual-purpose storage — general key-value snapshots plus an event log — using the Python standard-library sqlite3 module in WAL mode, opted into via the SZP_DB_PATH environment variable:

Behavior modeCondition
Pure in-memory (v2.0-compatible)SZP_DB_PATH unset
SQLite persistenceSZP_DB_PATH set

API design: store.put(key, value) (write a key-value snapshot), store.get(key, default=None) (read a key), store.append_event(type, payload) (append to the event log, for blockchain-style replay), store.replay_events(type) (replay the event log to restore state on process startup).

Verification: tests/test_v21_resilience.py uses subprocess.Popen to really launch the chain_sim.py subprocess, sends a real HTTP mint request, sends a real SIGTERM via proc.terminate(), confirms the process has actually terminated, then relaunches a new subprocess against the same database file (simulating a post-crash restart) and verifies balances and NFT holdings are correctly restored. A control-group test with SZP_DB_PATH unset confirms v2.0-compatible behavior remains unbroken.

Overhead measurement: local mint-transaction latency was compared between pure-in-memory mode and SQLite-persistence mode (10 samples each, both including the 120ms simulated confirmation delay):

ModeMean latencyP95 latency
Pure in-memory (v2.0-compatible)125.49 ms122.48 ms
SQLite persistence (v2.1 new)123.11 ms123.28 ms

The persistence write overhead falls within measurement noise (difference < 3ms, far below the scale of the 120ms simulated confirmation delay), demonstrating that SQLite's WAL mode adds essentially zero extra latency under this sandbox's write load.

2.2　Domain B/C: Real Royalty Settlement (EIP-2981 Enforced) & Asset Transfer

Problem: v2.0's royalty_bps field existed on mint requests but was never actually deducted or distributed on any transaction path, and NFTs could not change ownership at all.

Solution: chain_sim.py adds a /contract/transfer endpoint implementing the rule royalty_amount = sale_price × royalty_bps / 10000, seller_proceeds = sale_price − royalty_amount. The royalty beneficiary is fixed as that NFT's original minter (via a minter_of mapping), regardless of how many times it changes hands — matching EIP-2981's core semantic that creator royalties follow the asset across every secondary-market transaction. The same endpoint also supports peer-to-peer transfers of the fungible token (token_id=0), which does not trigger royalty logic.

Lifecycle verification example (tests/test_royalty_and_transfer.py::test_resale_pays_royalty_to_original_minter_not_seller):

StepActionAlice (creator) balanceBob balanceRoyalty flow
0Alice mints an NFT, royalty_bps=1000 (10%)00—
1Bob buys from Alice for 100 SZP100.0 (90 net + 10 royalty)900.0 (1000 − 100)10 SZP → Alice
2Carol buys from Bob for 200 SZP120.0 (+20 royalty)1080.0 (900 − 100 + 180)20 SZP → Alice (the original creator, not seller Bob)

The second resale verifies that royalties correctly flow to the original creator rather than the current seller — the point where EIP-2981 semantics are most easily implemented incorrectly — and this is now covered by a dedicated test assertion. A settlement-service proxy endpoint, /settle/transfer, was added to settlement_service.py so users can call the on-chain transfer through the settlement service proxy without holding direct chain-connection details.

2.3　Domain D: Structured Logging (JSON Lines)

Problem: v2.0 only emitted human-readable text via print(..., flush=True), which log-aggregation systems cannot parse and which cannot be filtered or queried programmatically.

Solution: a new src/structured_log.py module gives every service process a named logger; calling log.info(event_name, **fields) simultaneously emits a human-readable summary to stderr (preserving terminal-demo readability) and a structured JSON record to logs/<service>.jsonl (when SZP_LOG_DIR is set). The state_restored event is itself direct evidence that the persistence mechanism is working — the log shows exactly how many blocks were restored from the database at process startup.

2.4　Domain E: Expanded Anti-Cheat Rules

Problem: v2.0's anticheat.py had only one behavioral rule ("consecutive high-difficulty instant answers"), unable to defend against bot-driven farming or multi-account abuse patterns.

Solution: AntiCheatEngine expanded from a single rule to four independent rules working together:

Rule #Rule nameTrigger conditionVersion
1Signature verificationHMAC-SHA256 signature mismatchv2.0
2Consecutive high-difficulty instant answers3 consecutive questions of difficulty ≥3 answered in <2 secondsv2.0
3Rate limiting>20 events in a 10-second sliding windowv2.1 new
4Device-fingerprint clusteringSame device fingerprint tied to >5 distinct users within 60 secondsv2.1 new

Triggering any rule moves the account into held_for_review (a temporary hold pending human review, not a permanent ban); the reasons field records which rule(s) fired, for manual-review traceability. The risk-control profile can optionally persist through src.persistence, so risk-control history survives a process restart, closing the loophole of "restart wipes the risk record clean."

Rules 3 and 4 trigger-timing measurement (from the Stage 7 demo): rate limiting fired on the 21st event (threshold 20, so the 21st event triggers rate_limit_exceeded); device-fingerprint clustering fired on the 6th distinct user (threshold 5, so the 6th user sharing that device fingerprint triggers device_fingerprint_cluster). Both trigger points match the design threshold exactly (threshold + 1 triggers), confirming the sliding-window counting logic is correct.

2.5　Domain F: API Versioning

Problem: every v2.0 endpoint path was fixed (e.g. /contract/mint), leaving no smooth migration path for a future breaking change.

Solution: httpkit.py's JsonHTTPServer.route() / route_prefix() decorators now auto-register both paths: registering /contract/mint automatically also registers a /v1/contract/mint alias, both pointing to the same handler, guaranteeing identical behavior (the same function object, not duplicated logic). The unprefixed path remains available so existing v2.0 callers work unmodified; new callers are encouraged to standardize on the /v1 prefix. This design is a standard API-evolution transition-period convention: if a future v3 needs a breaking change, a /v2 prefix can coexist alongside it, with /v1 and the unprefixed path marked deprecated rather than removed outright.

A complete OpenAPI 3.0 spec document (docs/openapi.yaml) was produced alongside this, covering 16 path definitions across all four service processes, including request/response schemas, annotations for v2.1's new endpoints, and a description of the API versioning policy.

2.6　Domain G: Chaos-Testing Framework

Problem: the v2.0 plan mentioned a "chaos mode" concept, but no code implemented it — the disconnection scenario in launch_phase5.py was a one-time, scripted disconnect, not random fault injection.

Solution: a new src/chaos.py module provides three composable fault-injection primitives: ProcessKiller (sends a termination signal to a subprocess with a given probability, simulating an accidental crash during real operations), LatencyInjector (inserts random delay before a call, verifying whether timeout and retry settings are sufficiently tolerant), and FaultInjector (raises an exception on a call with a given probability, simulating packet loss or a dropped connection). A ChaosReport aggregates statistics on injected fault types alongside invariant-check results — e.g. "total minted − total burned = circulating supply" or "the same tx_id was only ever settled once" — giving the question "did the system hold up under chaos?" a structured, visualizable answer.

Real-scenario verification (tests/test_chaos.py::TestChaosRealProcessRestart): a real chain_sim.py subprocess runs through three rounds of "launch → mint → supply-conservation check → SIGTERM terminate," all against the same SQLite database path throughout, verifying that supply is conserved exactly (error < 1e-6) after every single restart.

2.7　Domain H: Dashboard v2

Problem: the v2.0 dashboard only showed process liveness and performance-spec comparisons — no on-chain asset overview, risk-control status, or chaos-test results.

Solution: src/dashboard.py adds five new rendering blocks: auto-refresh polling (an embedded <meta http-equiv="refresh"> that reloads the page periodically); on-chain asset overview (circulating supply, cumulative mints/burns, total NFT count, and cumulative royalties paid, shown as cards); a risk-control events block (listing users currently held_for_review and the rules that triggered it); a chaos-test report block (fault-type statistics paired with pass/fail invariant-check results in a table); and a persistence-status badge (marking each process's health check with either "persistent" or "pure in-memory — lost on restart"). The dashboard generator keeps v2.0's static-HTML-snapshot design philosophy; all new blocks are optional parameters that are automatically omitted when not supplied, keeping full backward compatibility with v2.0 callers.

6.2　Continuation and extension of the test-design principles

v2.1 continues v2.0's "real subprocess + real socket" integration-testing philosophy, and extends that principle further to real process termination and restart: both test_v21_resilience.py and test_chaos.py launch independent Python processes with subprocess.Popen, send a real SIGTERM via proc.terminate(), confirm the process actually terminated, and only then restart and verify — rather than simulating a restart with a mock or monkeypatch.

6.3　One-click demo reproducibility verification

run_all_demos.py was run 3 times during this rewrite effort (including the test-suite self-check inside Stage 7), with consistent results each time: 9/9 stages succeeded, with total durations landing in the 33–36 second range (the variance comes from normal scheduling jitter plus the random timing of chaos-test terminations).

Reaffirming the core boundary principle

Every "genuinely achieved" claim in v2.1 refers to real execution within this sandbox environment, at the rule and program-logic level (for example, a royalty was really deducted; a process was really terminated and restarted). Anything touching the real outside world (a real testnet, the Storacha cloud, a real device build) remains within the outlook scope already disclosed in v2.0, and improvements in v2.1's other domains do not blur that boundary.

11　Known Limits & Outlook

11.1　This sandbox's environment limits (carried over from v2.0; unchanged by v2.1)

  • Could not build a real Tauri client shell (no Rust/cargo toolchain)
  • Could not connect to a real IPFS node or the Storacha cloud service (no network access)
  • Could not deploy to a real EVM testnet (no network access)
  • Could not run large-scale concurrency/stress testing (single-machine sandbox resource limits)
  • SQLite persistence is a single embedded database file, with no distributed high-availability capability

11.2　Remaining Stage 7 outlook scope (per the plan's T8-01/T8-02) after v2.1

v2.1 has moved the following items from "planning concept" to "genuinely working at the rule level," but full production readiness still awaits:

  • Real Tauri five-platform (Windows/macOS/Linux/iOS/Android) builds and installer testing
  • Real Storacha cloud-persistence integration testing (v2.1's SQLite persistence solves only single-machine restart survival, not cloud multi-node high availability)
  • Real testnet (e.g. Sepolia) contract deployment and gas-cost measurement (v2.1's royalty-settlement logic can now serve as a reference baseline for the contract logic)
  • Large-scale concurrency stress testing and decentralized-compute-layer (Oracle) integration
