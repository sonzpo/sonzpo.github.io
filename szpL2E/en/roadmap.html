1　Reorganization Principles: Why "Process Count × Feature Depth"

Picture the whole production-readiness effort as a grid: the horizontal axis is "how many independent processes this system currently runs," the vertical axis is "how many feature layers this system currently has." Hold the horizontal axis fixed, stack the vertical axis up to a height that's "sufficient but honest," then move one column right to add another process.

Primary axis

Process count

A decentralized posture needs process count as the most honest observable metric; one-click-script complexity is driven mainly by process count and heterogeneity; each stage's launch script naturally doubles as the next stage's smoke-test baseline.

Secondary axis

Feature depth

Features depend on each other far more tightly than they appear to: anti-cheat and signature-based identity verification only make sense with two-process mutual trust; szpEX's CoW/Wormhole dual-routing decision logic likewise only makes sense at two-or-more-process scale.

Third axis

Evidence tier

Aligned with Chapter 19 of the Task Breakdown & Fishbone Plan v2.0's four-tier framework: spec frozen, rule-simulation verified, real-integration verified, production verified — plus a new "performance-benchmark comparison" as an extension of tier-one numeric simulation.

4　Detailed Stage-by-Stage Breakdown

4.1　Stage −1・Tauri Client Scaffold One-Click Demo

Launches 1 Tauri v2 client-shell process and 1 minimal local service process, verifying the full chain: frontend UI layer → IPC Bridge → Rust core → the Rust core calling the local service process via HTTP to fetch a static response. This stage involves no keys, no learning logic, and no on-chain logic — purely verifying "the client shell compiles, runs, and can handshake with a service process."

4.2　Stage 0・Single-Process Learning-Verification Core One-Click Demo

Launches 1 Python service process, running the F1-defined multi-track course units, spaced-repetition test scheduling, question-weighting, and scoring system through a ready-made end-to-end demo, with that process's automated tests folded into the launch script's self-check step. Token points are a purely in-memory simulation.

4.3　Stage 1・Single Process + Simulated On-Chain Settlement (Groundwork)

Still just 1 externally visible service process, but internally the in-memory token-point simulation from Stage 0 is upgraded to call a local embedded testnet for real contract transactions, against an ERC-1155／ERC-721＋EIP-2981 core-contract subset aligned to the F4 spec (implementing only the mint and burn functions).

4.4　Stage 2・Two Processes + Real Local-Chain Broadcast and IPFS/Storacha Prototype

Splits into 2 externally visible independent processes — the learning-verification service and the on-chain settlement service (including the local testnet) — communicating over real HTTP／RPC; learning-outcome summaries and course content also move to an IPFS＋Storacha hybrid persistence prototype, replacing the local file access used in Stages 0 and 1.

4.5　Stage 3・Two Processes + Anti-Cheat and Identity Spoofing Defense (Layered)

Process count stays at 2; on top of Stage 2's on-chain settlement, adds the F2-defined minimal anti-cheat behavior-analysis layer and signature-based identity verification, so every score sent from the learning side to the settlement side carries a verifiable signature and risk-control flag.

4.6　Stage 4・Multi-Process + Decentralized Topology and Monitoring Prototype

Process count expands to 3–6; adds an IPFS＋Storacha storage-proxy process and the Tauri client-shell process (running alongside the service-side processes for the first time), with a simple monitoring dashboard showing each process's health and data flow at a glance.

4.7　Stage 5・Multi-Process + szpEX Wallet／Asset-Monetization Integration and Resilience

Process count stays at 3–6; on top of Stage 4's topology, adds a minimal szpEX self-custody wallet (local key management + social-recovery prototype, without connecting to real CoW Protocol／Wormhole Bridge) and a corporate-task posting-interface prototype, plus resilience for the settlement process — auto-reconnect and event replay after a disconnect.

4.8　Stage 6・Multi-Process + Performance Spec and Monitoring Dashboard One-Click Demo

Process count stays at 3–6; on top of the process topology already live in Stages 4 and 5, the one-click launch script runs an extra pass of "numeric simulation + spec comparison," displaying the Performance Spec & Operations Manual v1.0's quantified SLA targets side-by-side with local simulated measurements on the monitoring dashboard, explicitly labeled as simulated values.

⚠ Stage 7・Production-Environment Sign-Off (Outlook, Outside One-Click Scope)

Real mainnet deployment, real-fund integration via CoW Protocol／Wormhole Bridge, third-party security audits, external educational-integrity assessment, real five-platform device benchmarking — these tasks cannot, by their nature, be compressed into the "local one-click launch" definition. They correspond to Chapter 19 "Evidence Tier Three: Production Verification" in the Task Breakdown & Fishbone Plan v2.0, and have not yet been broken down into a detailed WBS.

5　Technical Risk and Dependencies

5.1　Cross-Stage Critical Path

Stage −1 → Stage 0 → Stage 1 → Stage 2 → Stage 3 (layered)／Stage 4 → Stage 5 (layered) → Stage 6 (performance comparison) → Stage 7 (outlook)

A clear linear dependency runs across the nine build stages: Stage −1's Tauri client scaffold is the common starting point for client-shell integration from Stage 4 onward; Stage 0's learning-verification core is the shared starting point for Stages 1 through 6; Stage 2's two-process communication interface and storage proxy are the common foundation for both Stage 3's layered signature defense and Stage 4's expanded process count. A problem in any one stage's foundation directly drags down every cell to its right and above it.

⚠ Risk 6　Tauri／Rust toolchain cross-platform differences

First becomes a gating issue in Stage −1, corresponding to the environment-version prerequisite for the T0-05 no-persist private-key security-boundary risk node. Development machines on different platforms (Windows／macOS／Linux) require different system dependencies for a Tauri build; if the target environment is missing a dependency, every stage from Stage −1 onward that depends on the client shell will be blocked. Recommendation: run a minimal build on at least two mainstream development platforms first, to confirm the build process is reproducible.

⚠ Risk 7　The performance-comparison table's simulated values could be misread as official sign-off data

Surfaces in Stage 6, because simulated values and real local measurements are displayed side-by-side on the same dashboard; a careless visual-design choice could lead a user to mistake "the performance numbers shown in the one-click demo" for the official sign-off results in the Performance Spec & Operations Manual v1.0. Recommendation: simulated values should always carry a distinct background color or explicit label — "simulated estimate, not a real-device measurement" — with a fixed note underneath the comparison table explaining where the official sign-off data comes from.
