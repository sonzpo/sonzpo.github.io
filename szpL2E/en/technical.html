1　Overall Architecture Principles

Defining "no backend server" correctly

Before diving into technology choices, one premise needs to be settled: at szpL2E's target scale (cross-chain trading, an IP licensing market, a course platform, and future ERP/prediction markets), "literally zero servers anywhere" is not realistic, nor is it how decentralized applications (dApps) actually operate in the industry. The reasonable, achievable architectural goal is no single trusted server (No Trusted Central Server) — not literally "no compute nodes at all."

Concretely, szpL2E pursues three principles:

  1. No centralized business-logic server: matching, authentication, fund custody, and other core business logic never run on a server that szpL2E operates and can unilaterally control.
  2. Keep lightweight, stateless infrastructure anyone can re-run: RPC nodes, IPFS gateways, on-chain event indexers, for example. These are "trust-minimized," not "absent" — anyone can stand up a peer node to replace the one szpL2E provides.
  3. Replace the traditional backend API with smart contracts and off-chain protocols (Intent-Based Protocol): trade matching, asset transfer, and content licensing are instead handled by the user signing an "intent" with their wallet, executed by a decentralized solver/relayer network, and finally settled on-chain.

This mirrors how mature decentralized protocols such as CoW Protocol and Wormhole already operate: on-chain settlement, off-chain solver/relayer execution, and clients signing intents directly. szpL2E's architecture follows this same pattern as its main axis.

2.2.1　Anti-Cheat Verification & Question-Type Weighting

The verification mechanism is the product's most critical moat. If verification is too loose, token rewards collapse into meaningless grinding, wrecking both the economic model and educational credibility. The core design includes spaced-repetition testing (the same knowledge point resurfaces at 1/3/7/14-day intervals, with full reward only after repeated correct answers across intervals), typing/action-speed anomaly detection, and device/behavioral fingerprint matching.

Question typeVerification strengthToken weight
Multiple choiceLow (easy to guess／cheat)Base weight 1x
Scenario-based applicationMedium (requires understanding and reasoning)Weight 2–3x
Hands-on／project submissionHigh (requires real work and output)Weight 4–6x
Corporate-set taskHighest (corporate review + hands-on)Weight 6–10x ＋ corporate sponsorship bonus

2.3　The Token Economy's Deflationary Design

Token issuance follows a decaying curve: reward multipliers are highest early on to drive adoption, then step down per question as a user's level and the token's total circulating supply rise, dynamically pegged to "current circulating supply." Combined with fixed-ratio token burns across multiple spending scenarios — unlocking advanced content, minting credentials, entering lotteries — this creates self-adjusting deflationary pressure.

MetricDefinitionEffect on rewards
Progress coefficientTime-series growth in test accuracy and hands-on quality scoresConsistent improvement earns a multiplier bonus; stagnation or regression lowers it
Retention coefficientRegular learning cadence across cycles (not single-day binges)Regular learners get a stable multiplier; short bursts followed by disappearance earn no compounding bonus
Quality coefficientHuman or AI review score on hands-on work／projectsLow-quality output cannot be offset by volume

Funds for corporate-sponsored tasks are pre-funded by the sponsoring company into a smart contract; the platform never advances or handles the flow of funds, all on-chain, further reducing the platform's own capital exposure and regulatory risk.

2.4　Monetization & Reward Sources

Corporate-sponsored tasks

Companies pay for résumé and ability data, ranked hands-on results, and priority-matching access (subject to user consent).

Ad placement

Non-intrusive brand content shown in learning breaks, targeted by content track, settled on actual impressions and completion-conversion.

Token staking

Staking unlocks advanced-content access; long-term stakers gain governance weight, while staking also acts as a token sink stabilizing price.

Credential monetization

Paid minting of verifiable credentials (NFT／SBT); companies can pay to issue an "enterprise-certified" version of a credential.

3　Cross-Platform Client Architecture: Tauri v2

Why this choice: szpL2E must support five runtime environments simultaneously — iPhone, Android, Windows, macOS, and Wasm Web — and its core logic touches highly sensitive operations such as key management and cryptographic signing, so the client framework was chosen to prioritize "one core logic, deployed everywhere, native-grade security." Tauri v2 (stable v2.10.1, released March 2026) fully supports Linux, macOS, Windows, Android, and iOS, with core logic written in Rust — currently the only mature cross-platform framework that covers both desktop and mobile from a single Rust core.

RequirementHow Tauri v2 addresses it
Unified five-platform deploymentiOS and Android targets share the same Rust core business logic as desktop, avoiding duplicated, fragmented development
Wasm web versionThe frontend is already web technology (React／Svelte／Vue); the Rust core can additionally compile to pure Wasm+Web
Wallet & crypto logicCPU-intensive work (signing, encryption) runs in Rust, 10–100× faster than Node.js
Lightweight, fast installUses the system's native WebView instead of bundling Chromium; install size can be as small as a few MB
Permission governancev2 introduces a capability-based permission model, replacing v1's one-time allowlist

3.2　Four-Layer Client Architecture

  1. Frontend UI layer: React／Svelte + TypeScript, written once and shared across platforms.
  2. Tauri IPC Bridge: inter-process communication between the frontend and the Rust core via invoke／emit.
  3. Rust core: covers szpEX wallet signing and key management (including hardware-wallet HID/USB communication), an embedded IPFS/libp2p node, a local encrypted database (SQLite + SQLCipher), and CoW SDK／Wormhole SDK call bridging.
  4. Compiled output: the native path compiles to iOS／Android／Windows／macOS／Linux executables; a second path compiles the Rust core to WebAssembly via wasm-pack, paired with the WebCrypto API to protect private keys, producing the Wasm web version.

This design ensures the "web version" and the "native version" share the exact same Rust security logic, rather than a second implementation rewritten in JavaScript — avoiding the risk of fragmented, hard-to-audit security logic. The runner-up option, React Native, would sacrifice the benefit of a shared Rust core across platforms and is not recommended as the primary architecture.

4　Decentralized Storage Layer: IPFS and Storacha

A plain IPFS node alone cannot guarantee long-term data availability — without anyone pinning it, content can vanish from the network at any time. Standard 2026 industry practice combines "IPFS content addressing" with an underlying persistence network. Storacha (formerly web3.storage) combines IPFS content addressing, Filecoin long-term persistence, and UCAN (User Controlled Authorization Networks)-style permissioning.

TierPurposeTechnical approach
Hot dataE-book covers, course thumbnails, UI assetsIPFS + Storacha (UCAN authorization)
Cold dataPurchased complete e-books, course video mastersFilecoin storage deals (via Storacha or directly via FVM)

4.3　Key Design for Content IP Protection

E-books and course content must never sit on the public IPFS network in plaintext. The correct flow: content is encrypted before upload and pushed to IPFS to obtain a CID; the decryption key is released via a smart contract upon purchase, using either Lit Protocol-style access-control conditions or a self-built threshold key-distribution service; the CID is only an address pointer to the encrypted package — the real access-control logic lives entirely on-chain, not behind a szpL2E server gate. At least two independent pinning／persistence services are recommended, to spread the risk of a single service's outage or policy change.

5　szpEX Sonzpo Trading Wallet: the Cross-Chain Trading Core

5.1　CoW Protocol: Best Same-Chain Pricing and MEV Protection

The CoW Protocol SDK supports intent-based trading, covering swaps, limit orders, TWAP, and programmable orders, across 11+ blockchain networks. It executes trades via batch auction, protecting users from front-running and sandwich attacks; CowShedSdk gives a plain EOA wallet smart-contract-account capabilities, enabling one-click composite flows such as "buy a course + swap tokens" in a single action; it also ships its own BridgingSdk, integrating multiple bridge providers.

5.2　Wormhole: Cross-Chain Asset Bridging

The Wormhole TypeScript SDK supports Native Token Transfers (NTT), Wrapped Token Transfers (WTT), CCTP (USDC-specific), and Settlement. WTT simplifies cross-chain asset transfer, suited to cross-chain game-asset scenarios; the SDK spans both EVM and non-EVM chains (e.g. Solana, Sui), leaving room for future expansion.

5.3　szpEX Integration Architecture

  1. Users initiate operations from the szpEX wallet (built into the app, non-custodial), which supports software keys (BIP-39/44, encrypted on the Rust side) and hardware-wallet connections (Ledger／Trezor).
  2. The routing decision layer branches by transaction type: same-chain swaps go through the CoW Protocol SDK; cross-chain transfers go through the Wormhole SDK; composite cross-chain-plus-swap transactions default to CoW's BridgingSdk, with Wormhole as the fallback bridging route — the two coexist to increase routing diversity and fault tolerance.
  3. Settlement finalizes on-chain, with szpL2E never needing a self-operated server in the flow of funds.

5.5　Social Recovery

Private keys are held entirely on the user's own device, encrypted locally — the szpL2E platform never custodies keys. To reduce the risk of a lost seed phrase, szpEX plans to integrate social recovery, letting a user designate several trusted contacts who can jointly approve account recovery via threshold signature (e.g. 2-of-3) if the key is lost, with no single party ever holding the complete private key. This is implemented via a smart-contract account (Account Abstraction), with the entire recovery flow executed on-chain.

7　Mid/Long-Term Module Roadmap: ERP, Prediction Markets, and Gaming

ERP module

Smart-contract bookkeeping + zk-Rollup

Continues the "smart-contract bookkeeping + frontend UI" architectural line, using zero-knowledge proofs to strengthen privacy so enterprise financial detail need not be public on-chain while remaining verifiable.

Prediction-market module

Conditional Tokens Framework

Modeled on the Polymarket／Gnosis Conditional Tokens Framework, which naturally pairs with CoW Protocol's batch-auction settlement and can directly reuse szpEX's existing trade-routing infrastructure.

Gaming module

Cross-chain-friendly token standard

In-game assets adopt a cross-chain-friendly token standard from the design stage, connecting directly to the Wormhole NTT protocol szpEX already integrates, avoiding a future rearchitecture to make assets portable across chains.

8　Risks and Reality Checks

⚠ Regulatory risk

Cross-chain bridging, IP/copyright trading, education services, plus the future ERP and prediction-market modules, span securities law, copyright law, and financial regulation across multiple legal domains. We recommend consulting a lawyer experienced in crypto and securities regulation early for a compliance review. This plan is a technical-architecture study only and does not constitute legal advice.

⚠ Cross-chain bridge security risk

Cross-chain bridges have historically been a favorite hacker target; Wormhole itself suffered a roughly $320M security incident in 2022. When integrating cross-chain bridging, szpL2E must implement multi-signature controls, third-party security audits, and evaluate insurance mechanisms to reduce user-asset risk.

⚠ The UX cost of "truly no server"

A no-backend architecture means no traditional customer-support system and no centralized anomaly-monitoring facility. szpL2E needs a much more complete in-app on-chain transaction tracking and error-recovery flow to make up for the gap in user support under a decentralized architecture; the UX design difficulty here will be significantly higher than in a typical centralized app.
